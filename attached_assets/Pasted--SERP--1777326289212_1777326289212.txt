Нужно доработать текущий сервис анализа конкурентности ключевых слов по Яндекс SERP.

ВАЖНО:
Не сносить текущую архитектуру и не переписывать сервис с нуля.
Не ломать уже работающую логику:
- загрузка ключей;
- выбор региона;
- запуск анализа;
- получение Wordstat/частотности, если уже есть;
- получение SERP;
- раскрытие деталей SERP по ключу;
- сохранение serp_details в отчёте;
- расчёт strong / near / partial;
- расчёт score;
- классификация A/B/C/D;
- экспорт результатов.

Задача — аккуратно расширить и улучшить сервис, чтобы он стал универсальным под разные ниши и корректно определял типы страниц и конкурентов.

Сейчас сервис уже умеет анализировать ключи и выдавать результат. В отчёте уже есть serp_details с подробной детализацией по топу выдачи. Но есть проблема: часть классификации страниц и конкурентов работает неуниверсально и местами использует признаки старой логики под другую нишу. Например, для недвижимости могут появляться типы вроде TOOL, CONVERTER, SAAS, upload-form, pricing и т.п. Для недвижимости это нерелевантно.

При этом сервис не должен стать только “под недвижимость”. Он должен быть универсальным, с возможностью выбирать нишу анализа.

Нужно добавить систему нишевых профилей и улучшить итоговую классификацию serp_details.

==================================================
1. Цель доработки
==================================================

Сервис должен уметь анализировать SERP универсально, но с учётом выбранной ниши.

В интерфейсе нужно добавить выбор ниши анализа.

В MVP реализовать минимум два режима:

1. Универсальный режим
2. Недвижимость

Остальные ниши можно заложить в структуру для будущего расширения:
- SaaS / сервисы
- E-commerce
- Локальные услуги
- Медицина / клиники
- Образование

==================================================
2. Главное правило
==================================================

Базовую логику конкурентности не менять.

Главный критерий остаётся прежним:

strong + near в органической выдаче

Сервис по-прежнему должен считать:

- сколько сильных совпадений в title органики;
- сколько near совпадений в title органики;
- сколько partial совпадений;
- совпадения в description;
- количество рекламы;
- SEO score;
- Ads score;
- итоговый score;
- класс A/B/C/D.

Новая логика должна быть дополнительным слоем поверх существующего анализа:

- определение типа страницы;
- определение типа конкурента;
- доменная fallback-классификация;
- нишевые рекомендации;
- более точное объяснение результата.

==================================================
4. Универсальный режим
==================================================

В универсальном режиме сервис не должен делать слишком узких выводов.

Типы страниц в универсальном режиме:

- MARKETPLACE — агрегатор / площадка
- BRAND_SITE — сайт бренда или компании
- LANDING — посадочная страница
- ARTICLE — информационная статья
- DIRECTORY — каталог / подборка
- FORUM — обсуждение
- DOCUMENT — документ / справочная страница
- UNKNOWN — не удалось определить

Типы конкурентов:

- DIRECT
- CLOSE
- INDIRECT
- NOT_COMPETITOR
- UNKNOWN

В универсальном режиме основной вес должен оставаться за strong/near совпадениями в SERP.

==================================================
6. Доменная fallback-классификация
==================================================

Это ключевая доработка.

Сейчас бывает так:
HTML страницы не загрузился, например из-за HTTP 429, и сервис ставит:

page_type_html: UNKNOWN
competitor_level: UNKNOWN
intent_coverage: NONE

Для известных доменов это неправильно.

HTML-анализ должен быть дополнительным слоем, а не единственным источником истины.

Если HTML не загрузился, но есть domain, title, description и text_match_level из SERP, сервис всё равно должен классифицировать результат по доменным и SERP-правилам.

Правило:

fetch_ok=false не должен автоматически приводить к competitor_level=UNKNOWN.

Пример правильной логики:

fetch_ok=false
domain=avito.ru
text_match_level=NEAR

=> page_type_domain=CLASSIFIEDS или REAL_ESTATE_AGGREGATOR
=> competitor_level=CLOSE или DIRECT
=> classification_comment должен содержать, что HTML не загружен, но применено доменное правило

Для недвижимости:

1. Если домен — cian.ru, avito.ru, realty.yandex.ru, domclick.ru, novostroy.ru, move.ru, m2.ru, n1.ru, mirkvartir.ru, etagi.com:
   - page_type_domain = REAL_ESTATE_AGGREGATOR или CLASSIFIEDS
   - competitor_level минимум CLOSE
   - если text_match_level = STRONG или NEAR, competitor_level = DIRECT

2. Если домен — сайт застройщика:
   - page_type_domain = DEVELOPER_SITE
   - если text_match_level = STRONG или NEAR, competitor_level = DIRECT или CLOSE

3. Если страница похожа на страницу конкретного ЖК:
   - page_type_domain/page_type_serp = RESIDENTIAL_COMPLEX_PAGE
   - если ключ содержит название ЖК, competitor_level = DIRECT
   - если ключ общий по городу/типу квартиры, competitor_level = CLOSE или INDIRECT

4. Если это банк/ипотечная страница:
   - page_type_domain/page_type_serp = BANK_MORTGAGE_PAGE
   - DIRECT только для ипотечных запросов
   - иначе INDIRECT

5. Если это информационная статья:
   - page_type_domain/page_type_serp = ARTICLE
   - при strong/near может быть CLOSE
   - при partial обычно INDIRECT

7. Итоговые поля в serp_details
==================================================

В serp_details нужно сохранить текущие поля и добавить/уточнить итоговую классификацию.

Добавить поля:

- niche
- page_type_domain
- domain_rule_applied: true/false
- html_status
- final_page_type
- final_competitor_level
- final_intent_coverage
- classification_source

Пример:

{
  "keyword": "купить однокомнатную квартиру в мытищах в новостройке",
  "position": 1,
  "domain": "www.avito.ru",
  "url": "...",
  "title": "Купить 1-комнатную квартиру в новостройке в Мытищах",
  "description": "...",
  "page_type_serp": "AGGREGATOR",
  "page_type_html": "UNKNOWN",
  "page_type_domain": "CLASSIFIEDS",
  "domain_rule_applied": true,
  "fetch_ok": false,
  "html_status": "HTTP 429",
  "text_match_level": "NEAR",
  "competitor_level": "DIRECT",
  "final_competitor_level": "DIRECT",
  "classification_source": "domain+serp",
  "classification_comment": "HTML не загружен: HTTP 429. Применено доменное правило для avito.ru и SERP-совпадение NEAR."
}

Если уже есть competitor_level, можно обновлять его итоговым значением, но желательно сохранить final_competitor_level отдельно для прозрачности.

8. Пересчёт агрегированных метрик
==================================================

После внедрения доменных правил нужно пересчитывать агрегированные показатели по ключу с учётом итоговой классификации.

Например, если в serp_details у avito.ru, cian.ru, domclick.ru раньше было UNKNOWN из-за fetch error, а теперь стало DIRECT/CLOSE, то в summary по ключу должны измениться:

- direct_count
- close_count
- indirect_count
- not_competitor_count
- unknown_count
- competitor_count
- рекомендация
- возможно score, если score учитывает competitor_level

Если score сейчас считается только по text match — не ломать формулу.
Если score уже учитывает competitor_level — использовать final_competitor_level.

9. Анализ статуса
==================================================

Добавить или уточнить analysis_status по каждому ключу:

- success
- partial_success
- serp_error
- api_key_missing
- empty_serp
- fallback_used
- mock_used

Если SERP получен, но часть HTML не загружена, это не ошибка всего ключа.
В таком случае:

analysis_status = partial_success

или

analysis_status = success_with_html_errors

Важно:
HTML 429 по отдельным страницам не должен обнулять анализ ключа, если SERP title/description получены.

10. Mock / fallback
==================================================

Проверить, нет ли в сервисе ситуации, когда при ошибке API возвращается красивый одинаковый результат как будто анализ успешен.

Если используется mock, он должен быть явно помечен:

analysis_status = mock_used

В интерфейсе и отчёте должно быть видно:

“Используется тестовая выдача, результаты нельзя использовать для SEO-решений”.

12. Рекомендации
==================================================

Рекомендация должна учитывать не только класс A/B/C/D, но и тип конкурентов.

Примеры для недвижимости:

Класс A:
“Очень низкая конкуренция, хороший кандидат для первой волны”

Класс B + много агрегаторов:
“Можно заходить, но выдача занята агрегаторами. Нужна сильная страница с подборкой, фильтрами, FAQ и перелинковкой”

Класс B + мало прямых конкурентов:
“Хороший кандидат, можно брать в первую партию страниц”

Класс C:
“Конкуренция заметная, лучше брать после низкоконкурентных страниц”

Класс D:
“Высокая конкуренция, не брать в первую волну”

Если анализ неуспешен:
“SERP не получен, решение по ключу принимать нельзя”

14. Критерии готовности
==================================================

Доработка считается готовой, если:

- сервис запускается без ошибок;
- текущая форма не сломана;
- можно выбрать нишу анализа;
- по умолчанию выбрана “Недвижимость”;
- известные real estate домены классифицируются корректно;
- avito.ru, cian.ru, domclick.ru, realty.yandex.ru не остаются UNKNOWN при STRONG/NEAR совпадении только из-за того, что HTML не загрузился;
- HTTP 429 / fetch_ok=false не обнуляет конкурентность результата;
- в serp_details есть новые поля итоговой классификации;
- direct_count / close_count / unknown_count считаются по итоговой классификации;
- по каждому ключу есть analysis_status;
- если используется mock/fallback, это явно видно;
- в раскрытии SERP видно, почему результат считается DIRECT/CLOSE/INDIRECT;
- базовая логика strong + near и score сохранена;
- экспорт не сломан.
