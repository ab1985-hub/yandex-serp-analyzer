Нужно доработать текущий внутренний сервис анализа конкурентности ключевых слов по Яндекс SERP.

ВАЖНО:
Это НЕ публичный пользовательский сервис.
Это внутренний рабочий инструмент.

Им будут пользоваться:
1. человек вручную через интерфейс;
2. другой ИИ-агент внутри общей системы.

В будущем другой ИИ-агент будет использовать результаты этого сервиса для принятия решений:
- какие ЖК парсить,
- какие квартиры парсить,
- куда идти дальше по логике SEO-машины.

Но сейчас задача НЕ в этом.

ТЕКУЩАЯ ГЛАВНАЯ ЗАДАЧА:
сделать так, чтобы сервис перестал работать на мок-данных и начал получать РЕАЛЬНЫЕ данные из выдачи Яндекса.

Сейчас видно, что сервис работает на демо-режиме:
- в интерфейсе есть пометка, что используются мок-данные;
- в деталях анализа видны искусственные URL типа mock-site-*;
- значит анализ пока идёт не по реальной выдаче.

НУЖНО ИСПРАВИТЬ ИМЕННО ЭТО.

ЧТО НУЖНО СДЕЛАТЬ

1. Найти в проекте, где сейчас используются мок-данные.
Нужно определить:
- где формируются mock organic results;
- где формируются mock ads results;
- где включается мок-режим;
- где backend решает использовать заглушку вместо реального источника данных.

2. Подключить реальный источник данных по Яндекс SERP.

Нужно, чтобы backend реально получал:
- органическую выдачу;
- рекламную выдачу;
- реальные title;
- реальные description/snippet;
- реальные url;
- реальные домены.

Если в проекте уже заложена интеграция с внешним SERP API — довести её до рабочего состояния.
Если не заложена — добавить аккуратно.

3. Сделать нормальную внутреннюю конфигурацию для подключения SERP-провайдера.

Не нужно строить логику под публичный продукт.
Нужно сделать просто рабочую внутреннюю интеграцию.

Сделай так, чтобы сервис мог работать через env-переменные / secrets в Replit.

Поддержи конфигурацию вида:
- SERP_PROVIDER
- SERP_API_KEY
или
- SERP_LOGIN
- SERP_PASSWORD

Если конкретный провайдер требует login/password — это нормально.
Если можно использовать API key/token — это даже лучше.

Главное:
другой ИИ-агент и человек не должны вводить это руками каждый раз.
Секреты должны один раз лежать в Replit Secrets / env и использоваться автоматически backend-сервисом.

4. Сделать так, чтобы backend при наличии настроенных credentials автоматически ходил в реальную SERP.

То есть:
- пользователь/агент отправляет ключи;
- backend сам обращается к внешнему источнику данных;
- получает реальную выдачу;
- запускает уже существующую логику анализа на реальных данных.

5. Если credentials не заданы:
- сервис может временно fallback в мок-режим;
- но это должно быть явно помечено в интерфейсе;
- и в коде это должно быть отдельным режимом, а не неявной подменой.

6. Не ломать уже сделанную аналитику.

Уже реализованы:
- текстовое совпадение;
- тип страницы;
- прямой конкурент;
- гео-релевантность;
- debug;
- детали анализа;
- русский интерфейс.

ЭТО НУЖНО СОХРАНИТЬ.

То есть задача не переписать сервис заново,
а заменить источник данных:
не мок-результаты, а реальные результаты Яндекса.

7. Убедиться, что после подключения реальной выдачи:
- в деталях анализа больше нет mock-site-*;
- отображаются реальные URL;
- отображаются реальные заголовки;
- отображаются реальные описания;
- по разным ключам результаты действительно различаются;
- сервис анализирует каждое ключевое слово отдельно.

8. Проверить работу end-to-end.

Нужно реально прогнать сценарий:
- открыть форму;
- вставить тестовые ключи;
- выбрать регион;
- запустить анализ;
- убедиться, что backend ходит за реальной выдачей;
- убедиться, что frontend показывает реальные результаты;
- убедиться, что debug строится на реальных данных.

9. Если для запуска нужны secrets, подготовить понятную схему.

Нужно:
- указать, какие secrets/переменные нужны;
- где именно они используются;
- как понять, что сервис уже работает на реальных данных, а не на моках.

10. В интерфейсе оставить явный индикатор режима.

Например:
- «Реальные данные SERP»
или
- «Мок-данные: API не подключён»

Это нужно, чтобы всегда было понятно, в каком режиме работает сервис.

ЧТО НЕ НУЖНО ДЕЛАТЬ СЕЙЧАС

Сейчас НЕ нужно:
- делать публичный кабинет;
- строить сложную систему ролей;
- делать многопользовательский доступ;
- делать отдельную агентную оркестрацию;
- реализовывать следующий этап по выбору ЖК и квартир.

Сейчас нужен только один шаг:
СЕРВИС ДОЛЖЕН ПОЛУЧАТЬ РЕАЛЬНЫЕ ДАННЫЕ ИЗ ВЫДАЧИ ЯНДЕКСА.

ЧТО ДОЛЖНО БЫТЬ В ИТОГЕ

После доработки:
- сервис работает на реальной SERP Яндекса;
- backend получает реальные title, description, url, domain;
- frontend показывает реальные результаты;
- существующая аналитическая логика работает уже поверх реальных данных;
- мок-режим остаётся только как fallback;
- в интерфейсе явно видно, используется реальный режим или мок-режим.

ПОСЛЕ ИСПРАВЛЕНИЯ ОБЯЗАТЕЛЬНО НАПИШИ

1. Где именно в проекте были мок-данные.
2. Какой реальный источник данных теперь подключён.
3. Какие env/secrets нужно задать в Replit.
4. Какие файлы ты изменил.
5. Что именно изменил в backend.
6. Что именно изменил во frontend.
7. Как теперь понять по интерфейсу, что сервис работает на реальной выдаче.
8. Подтверди, что анализ теперь идёт по реальным данным Яндекса, а не по заглушкам.

Сначала внеси реальные изменения в код, потом покажи итог.
