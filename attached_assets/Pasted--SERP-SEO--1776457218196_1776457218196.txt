Нужно доработать модель оценки SERP для SEO-машины, но не только по сниппетам выдачи. Для более точной оценки нужно добавить **углублённый анализ страниц из топа**.

Важно: не надо ломать текущий слой текстового совпадения по SERP. Он нужен и в целом работает нормально. Проблема в том, что сейчас итоговая оценка слишком сильно опирается на совпадение слов в сниппетах и слишком слабо понимает, что реально находится внутри страниц.

Нужна более правильная SEO-логика:
нам интересны не просто запросы, где мало совпадений, а запросы, где выдача **плохо или неполно закрывает интент пользователя**. Чтобы это понимать, нужно смотреть не только на SERP, но и на содержимое самих страниц из топа.

## Что нужно сделать

### 1. Сохранить текущий быстрый SERP-анализ

Текущий анализ по данным SERP нужно оставить как базовый слой:

* title
* description / snippet
* url
* домен
* совпадение по формулировкам запроса

Этот слой не выбрасываем. Он остаётся как быстрый первый проход.

### 2. Добавить второй слой: углублённый анализ страниц из топа

Нужно реализовать дополнительный этап:
после получения выдачи по ключу система должна уметь **догружать сами страницы из топа** и анализировать их содержимое.

На первом этапе не нужен тяжёлый браузерный рендеринг.
Достаточно обычного серверного HTTP-fetch HTML и разбора содержимого страницы.

Для каждой страницы из топа нужно пытаться достать хотя бы:

* final URL после редиректов
* `<title>`
* meta description
* H1
* первые текстовые блоки
* CTA / кнопки / формы
* признаки сервиса / инструмента / лендинга / статьи

Если часть страниц недоступна или плохо парсится — это нормально, просто помечать как частично проанализированные.

### 3. Ограничить глубину

Чтобы не убить производительность:

* анализировать не весь топ, а, например, только top 5 или top 10;
* сделать это только для детального анализа, а не для всех быстрых массовых расчётов;
* в массовом режиме можно оставить только SERP-layer;
* в детальном режиме — SERP + Page Analysis.

То есть нужен режим примерно такого типа:

* быстрый анализ = только SERP
* углублённый анализ = SERP + догрузка страниц

### 4. Что нужно определять по содержимому страницы

После догрузки HTML страницы нужно лучше определять:

#### Тип страницы

Минимально:

* `Инструмент / сервис`
* `SaaS / web-app`
* `Конвертер / транскрибатор / tool-page`
* `Лендинг продукта`
* `Документация / help / support`
* `Информационная статья`
* `Обзор / подборка / медиаматериал`
* `Маркетплейс / каталог`
* `Форум / user-generated`
* `Нерелевантный результат`

#### Прямой / близкий конкурент

Нужно определять:

* `Прямой конкурент`
* `Близкий конкурент`
* `Непрямой конкурент`
* `Не конкурент`

#### Насколько страница закрывает интент

Простая шкала:

* `сильно закрывает интент`
* `частично закрывает интент`
* `слабо закрывает интент`
* `не закрывает интент`

### 5. Какие признаки искать внутри страницы

Для определения сервисного / инструментального типа страницы нужно искать признаки внутри HTML:

#### Признаки tool / service / SaaS

* кнопки:

  * `попробовать`
  * `начать`
  * `загрузить`
  * `upload`
  * `convert`
  * `transcribe`
  * `start free`
  * `try now`
* формы загрузки файла
* drag-and-drop зоны
* CTA-блоки
* pricing / тарифы
* регистрация / sign up
* product / feature-блоки

#### Признаки статьи

* большой основной текст
* дата публикации
* оглавление
* блоки “читайте также”
* автор / редакция
* формат how-to / guide / blog / article

#### Признаки обзора / подборки

* списки сервисов
* сравнение инструментов
* “топ сервисов”
* “лучшие …”
* карточки нескольких продуктов

#### Признаки документации / help

* docs / help / support в URL
* технический стиль
* reference / API / manual-подобные блоки

### 6. Как использовать это в SEO-логике

Нужно сместить модель от логики:
`мало совпадений = хорошо`

к более правильной:
`топ плохо закрывает интент = возможность`

То есть итоговый score должен учитывать:

1. Текстовое совпадение по SERP
2. Тип страницы по сниппету
3. Тип страницы по реальному содержимому
4. Прямой / близкий конкурент
5. Насколько страница закрывает интент
6. Смешанность выдачи в целом
7. Силу домена / тяжесть результата, если это уже есть в проекте

### 7. Смешанность SERP

Нужно добавить оценку SERP в целом:

* `Однородная выдача`
* `Смешанная выдача`
* `Сильно смешанная / неопределённая выдача`

Логика:

* если в топе в основном один тип сильных страниц — выдача однородная;
* если в топе перемешаны статьи, сервисы, обзоры, форумы и случайные результаты — выдача смешанная.

Для SEO это важно:

* однородная выдача сильных конкурентов = сложнее;
* смешанная выдача = часто возможность;
* сильно смешанная выдача = Яндекс ещё не до конца определился, и это хороший шанс сделать более точную страницу.

### 8. Как это должно влиять на итоговую оценку

Нужно, чтобы итоговый score строился не в основном от совпадения слов, а по нескольким слоям.

Ориентир по смыслу:

* текстовое совпадение — низкий или средний вес;
* тип страницы — средний вес;
* прямой конкурент — высокий вес;
* сильное закрытие интента — высокий вес;
* смешанность SERP — высокий вес на уровне общего вывода;
* нерелевантные результаты почти не должны усиливать конкуренцию.

Принцип:

* много прямых конкурентов + страницы хорошо закрывают интент + выдача однородная = конкуренция выше;
* мало прямых конкурентов + выдача смешанная + интент закрывается слабо = хорошая SEO-возможность.

### 9. На чём проверить

После реализации нужно прогнать запрос:
`из аудио в текст`

И проверить:

1. Совпадение текста по SERP остаётся одним из сигналов.
2. Страницы сервисов / transcription tools не помечаются как нерелевантные.
3. После догрузки страниц такие результаты чаще определяются как:

   * `Инструмент / сервис`
   * `Прямой конкурент`
   * `сильно закрывает интент`
4. Статьи и обзоры не приравниваются по весу к инструментам.
5. Итоговая оценка становится более реалистичной и опирается на структуру выдачи, а не только на текст сниппетов.

### 10. Ограничения реализации

Важно:

* не добавлять тяжёлый Playwright / Puppeteer на этом этапе, если можно обойтись обычным HTML-fetch;
* не ломать текущий интерфейс;
* не переписывать весь пайплайн с нуля;
* встроить это как усиление текущего детального анализа;
* если страница не парсится, не валить анализ целиком.

### 11. Что показать после доработки

После реализации покажите:

1. Какие новые слои оценки добавлены.
2. Какие признаки теперь берутся не только из SERP, но и из самих страниц.
3. По каким правилам теперь определяется:

* тип страницы
* прямой / близкий / непрямой конкурент
* насколько страница закрывает интент
* смешанная или однородная выдача

4. Повторный прогон запроса:
   `из аудио в текст`
5. Кратко:

* как было раньше
* как стало теперь
* почему итоговая оценка стала точнее с точки зрения SEO

Важно:
делайте это как улучшение текущей модели оценки SERP, а не как полный рефактор всего проекта.
