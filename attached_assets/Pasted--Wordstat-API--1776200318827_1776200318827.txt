Нужно добавить в Wordstat API и Комбинированный режим ещё один параметр: **минимальная частотность**.

Цель:
пользователь должен иметь возможность задать порог частотности, ниже которого ключи не попадают в итоговый список.

Пример:
если пользователь указал `50`, то все запросы с частотностью `< 50` должны быть исключены из итоговой Wordstat-таблицы и не должны попадать в дальнейший анализ.

## Что нужно сделать

### 1. Новый параметр в UI

Добавить в форму Wordstat API:

* новое поле `Минимальная частотность`

И аналогично в Комбинированный режим:

* новое поле `Минимальная частотность`

Тип поля:

* числовое input
* целое число
* минимально 0
* по умолчанию можно поставить `0`

Логика:

* `0` = не фильтровать по частотности
* `50` = оставить только ключи с частотностью `>= 50`

### 2. Где применять фильтр

Фильтр по частотности нужно применять **после получения данных из Wordstat `results`**, но **до**:

* показа таблицы пользователю;
* чекбоксов;
* экспорта;
* отправки в анализ;
* автоматического анализа в комбинированном режиме.

То есть pipeline должен быть таким:

1. получаем `results` из Wordstat;
2. убираем пустые / дубли;
3. применяем пользовательские минус-фразы;
4. применяем фильтр `частотность >= minFrequency`;
5. обрезаем по лимиту;
6. показываем итоговую таблицу.

Важно:
частотность должна фильтроваться **до лимита**, а не после.
Иначе пользователь поставит лимит 100, minFrequency 50, а внутри останется мало релевантных строк просто потому, что сначала отрезали лимитом, а потом начали фильтровать.

Правильный порядок:

* сначала фильтрация по частотности,
* потом лимит.

### 3. В каких режимах это должно работать

Обязательно:

* Wordstat API
* Комбинированный режим

Не нужно:

* Search API режим для ручного списка ключей

### 4. Поведение в Wordstat-режиме

Если пользователь:

* seed-key = `квартиры для семей с ребенком`
* minFrequency = `50`

То в таблице остаются только ключи с частотностью `>= 50`.

Например:

* `600` → оставить
* `123` → оставить
* `59` → оставить
* `47` → исключить
* `43` → исключить

### 5. Поведение в Комбинированном режиме

Та же логика:

* сначала Wordstat собирает ключи;
* применяет минус-фразы;
* применяет minFrequency;
* применяет лимит;
* затем только оставшиеся ключи уходят в Search API анализ.

### 6. Изменения в фронте

Ожидаемо нужно обновить:

* `WordstatForm`
* форму комбинированного режима
* `HomePage` или родительский контейнер состояния

Нужен новый state, например:

* `wordstatMinFrequency`
* `combinedMinFrequency`

Или общий, если архитектура уже позволяет.

### 7. Изменения в backend

Нужно, чтобы backend endpoint Wordstat принимал новый параметр, например:

* `min_frequency`

И применял его к результатам Wordstat до лимита.

То есть endpoint типа `/api/wordstat/top` должен учитывать:

* phrase
* region
* limit
* minus phrases
* min frequency

А комбинированный сценарий должен использовать тот же фильтр в той же логике.

### 8. Важные требования

* не ломать текущую таблицу Wordstat;
* не ломать чекбоксы;
* не ломать перенос минус-слов;
* не ломать экспорт;
* не менять логику Search API режима;
* не смешивать `results` и `associations`.
