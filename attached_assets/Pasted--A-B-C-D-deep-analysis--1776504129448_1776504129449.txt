Нужно исправить итоговую классификацию A/B/C/D. Сейчас deep-analysis уже правильно видит структуру выдачи, но итоговый класс иногда остаётся слишком оптимистичным.

Проблема на примере запроса:

`преобразовать аудио в текст`

В деталях видно:

* SERP = однородная выдача;
* большая часть top-10 — `TOOL_SERVICE / CONVERTER / SAAS`;
* много прямых конкурентов;
* у многих страниц интент = `STRONG`;
* в рекомендации написано, что заходить сложно;
* но итоговый класс может оставаться `A`.

Это неправильно.

При этом важно **не перегнуть в другую сторону**.
Не нужно автоматически занижать все tool-запросы до `C/D`. Если выдача смешанная, часть результатов — статьи, часть — сервисы, и прямых конкурентов немного, класс `B` может быть нормальным.

Нужно не переписывать всю формулу, а добавить аккуратные guardrails поверх текущего score.

---

## 1. Что нужно посчитать по каждому ключу

После deep-analysis по каждому ключу посчитать:

```ts
total_results = количество органических результатов в top-10

html_loaded_count = количество результатов, где fetch_ok = true

direct_count = количество результатов, где competitor_level = DIRECT

close_count = количество результатов, где competitor_level = CLOSE

indirect_count = количество результатов, где competitor_level = INDIRECT

not_competitor_count = количество результатов, где competitor_level = NOT_COMPETITOR

strong_intent_count = количество результатов, где intent_coverage = STRONG

partial_intent_count = количество результатов, где intent_coverage = PARTIAL

tool_like_count = количество результатов, где page_type_html входит в:
- TOOL_SERVICE
- CONVERTER
- SAAS
- LANDING

article_like_count = количество результатов, где page_type_html входит в:
- ARTICLE
- REVIEW_LIST
- DOCS
- FORUM

unloaded_count = количество результатов, где fetch_ok = false
```

Важно:
`direct_count`, `close_count`, `strong_intent_count`, `tool_like_count` и `serp_mix` должны участвовать не только в debug-выводе, но и в финальном определении класса A/B/C/D.

Если `fetch_ok = true`, приоритет у HTML-layer.
Если `fetch_ok = false`, можно использовать базовую SERP-оценку для score, но в debug нужно честно показывать `Не загружено`.

---

## 2. Нормализовать доли

Также посчитать:

```ts
direct_ratio = direct_count / total_results
close_ratio = close_count / total_results
strong_intent_ratio = strong_intent_count / total_results
tool_like_ratio = tool_like_count / total_results
loaded_ratio = html_loaded_count / total_results
```

Если `total_results = 0`, guardrails не применяются.

---

## 3. Значение классов

Классы должны означать:

```text
A = низкая конкуренция / хороший кандидат
B = умеренная конкуренция / можно брать в работу
C = высокая конкуренция / заходить осторожно
D = очень высокая конкуренция / плотная выдача
```

---

## 4. Guardrails без перегиба

Сначала считается текущий score и текущий класс как сейчас.
Потом поверх результата применяются следующие правила.

---

# 4.1. Когда класс A запрещён

Класс `A` запрещён, если выполняется хотя бы одно условие:

```ts
direct_count >= 4
```

или

```ts
direct_count >= 3 && serp_mix.label === "HOMOGENEOUS"
```

или

```ts
tool_like_count >= 6 && strong_intent_count >= 5
```

или

```ts
strong_intent_count >= 7
```

Если базовая формула дала `A`, но одно из этих условий сработало, поднять класс минимум до `B`.

Важно:
`A` не должен появляться там, где в top-10 уже много прямых сервисов или много страниц сильно закрывают интент.

---

# 4.2. Минимум B

Если выполняется хотя бы одно условие:

```ts
direct_count >= 4
```

или

```ts
strong_intent_count >= 6
```

или

```ts
tool_like_count >= 7
```

то итоговый класс не может быть лучше `B`.

То есть если текущая формула дала `A`, заменить на `B`.

---

# 4.3. Минимум C

Класс должен быть минимум `C`, если выполняется хотя бы одно условие:

```ts
direct_count >= 5 && strong_intent_count >= 5
```

или

```ts
direct_count >= 4 && tool_like_count >= 6 && serp_mix.label === "HOMOGENEOUS"
```

или

```ts
tool_like_count >= 7 && strong_intent_count >= 6 && serp_mix.label === "HOMOGENEOUS"
```

или

```ts
direct_count >= 5 && serp_mix.label === "HOMOGENEOUS"
```

То есть:

* много прямых конкурентов само по себе — ещё не всегда `C`;
* но много прямых конкурентов + сильное закрытие интента / tool-like выдача / однородная выдача = минимум `C`.

---

# 4.4. Класс D

Класс `D` ставить только для реально плотной выдачи.

`D` должен быть, если выполняется хотя бы одно условие:

```ts
direct_count >= 7 && strong_intent_count >= 7 && serp_mix.label === "HOMOGENEOUS"
```

или

```ts
direct_count >= 8
```

или

```ts
direct_count >= 6 && tool_like_count >= 8 && strong_intent_count >= 7 && serp_mix.label === "HOMOGENEOUS"
```

Важно:
не ставить `D` просто потому, что запрос инструментальный.
`D` — это когда выдача реально плотно занята прямыми конкурентами, которые сильно закрывают интент.

---

## 5. Когда A всё ещё допустим

Класс `A` допустим, если одновременно:

```ts
direct_count <= 3
```

и

```ts
strong_intent_count <= 5
```

и

```ts
tool_like_count <= 5
```

и

```ts
serp_mix.label !== "HOMOGENEOUS" || direct_count <= 2
```

То есть:

* если прямых конкурентов мало;
* выдача не плотно занята одним сильным типом страниц;
* интент не закрыт большим количеством сильных страниц;

тогда `A` может быть допустим.

---

## 6. Когда B допустим

Класс `B` допустим, если:

```ts
direct_count <= 4
```

и

```ts
strong_intent_count <= 6
```

и

```ts
tool_like_count <= 7
```

и не сработали условия минимума `C`.

Это важно для смешанных выдач.

Например:
`как перевести аудио в текст`

Если там:

* часть статей,
* часть сервисов,
* выдача смешанная,
* прямых конкурентов немного,

то `B` может быть нормальной оценкой.

---

## 7. Согласовать score и класс

После применения guardrails score должен соответствовать классу.

Если в проекте уже есть текущие пороги классов — использовать их.

Если текущие пороги такие:

```text
A: 0–9.99
B: 10–19.99
C: 20–29.99
D: 30+
```

то после guardrails:

```ts
если класс стал B, score = max(score, 10)
если класс стал C, score = max(score, 20)
если класс стал D, score = max(score, 30)
```

Если пороги в проекте другие, не менять шкалу молча. Использовать текущие пороги проекта, но обеспечить главное правило:

**score и класс не должны противоречить друг другу.**

---

## 8. Согласовать рекомендацию с классом

Рекомендация должна соответствовать классу.

### Для A

```text
Низкая конкуренция: прямых конкурентов мало, выдача не закрыта плотными сервисами. Хороший кандидат для SEO-продвижения.
```

### Для B

```text
Умеренная конкуренция: есть релевантные результаты, но выдача не полностью занята прямыми конкурентами. Можно брать в работу.
```

### Для C

```text
Высокая конкуренция: в топе заметная доля прямых или близких конкурентов, заходить осторожно.
```

### Для D

```text
Очень высокая конкуренция: выдача плотно занята прямыми конкурентами, интент хорошо закрыт. Продвижение будет сложным.
```

Запрещены противоречия:

* класс `A` + рекомендация “заходить сложно”;
* класс `C/D` + рекомендация “отличный кандидат”;
* много прямых конкурентов + текст “конкурентов почти нет”.

---

## 9. Добавить пояснение guardrail в debug

В debug-данные для каждого ключа добавить поле, например:

```ts
class_guardrail_reason
```

или

```ts
classification_adjustments
```

Если класс был скорректирован guardrail-ом, нужно показать причину.

Примеры:

```text
Класс повышен до B: direct_count=4
```

```text
Класс повышен до C: direct_count=5, strong_intent_count=5
```

```text
Класс повышен до D: direct_count=7, strong_intent_count=7, serp_mix=HOMOGENEOUS
```

```text
Класс A запрещён: tool_like_count=6, strong_intent_count=5
```

Это нужно, чтобы было понятно, почему итоговый класс изменился.

## 10. Что проверить

После исправления прогнать 3 запроса.

---

### Запрос 1

```text
преобразовать аудио в текст
```

Ожидание:

Если в top-10:

* direct_count >= 5
* strong_intent_count >= 5
* serp_mix = HOMOGENEOUS

то класс должен быть минимум `C`.

Если:

* direct_count >= 7
* strong_intent_count >= 7
* serp_mix = HOMOGENEOUS

то класс должен быть `D`.

---

### Запрос 2

```text
аудио в текст онлайн
```

Ожидание:

Если:

* direct_count >= 7
* strong_intent_count >= 7
* serp_mix = HOMOGENEOUS

то класс должен быть `D`.

Если прямых конкурентов меньше, но:

* direct_count >= 5
* strong_intent_count >= 5

то минимум `C`.

---

### Запрос 3

```text
как перевести аудио в текст
```

Ожидание:

Если выдача смешанная:

* часть статей,
* часть сервисов,
* прямых конкурентов не больше 4,

то `B` может быть допустим.

Не нужно автоматически поднимать такую выдачу до `D`.

---

### Запрос 4

```text
конспект лекции
```

Ожидание:

Если:

* direct_count <= 3
* tool_like_count <= 5
* strong_intent_count <= 5

то класс `A` или `B` допустим.

Если там в основном статьи и нет прямых сервисов, класс `A` может быть корректен.

---

## 11. Что показать после исправления

Покажите по каждому из 4 запросов:

```text
ключ
итоговый класс
итоговый score
serp_mix
direct_count
close_count
strong_intent_count
tool_like_count
html_loaded_count
class_guardrail_reason
рекомендация
```

Главная цель:
итоговый класс должен соответствовать реальной структуре выдачи.

Если deep-analysis показывает плотную однородную выдачу из прямых сервисов, запрос не может получать класс `A`.

Но если выдача смешанная и прямых конкурентов немного, не нужно искусственно завышать сложность до `C/D`.
