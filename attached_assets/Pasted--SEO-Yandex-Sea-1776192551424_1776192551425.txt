Нужно переработать текущую SEO-машину в сервис-анализатор конкуренции на базе официальных Yandex Search API и Wordstat API, полностью отказавшись от парсинга публичной выдачи Яндекса.

Работай как сильный full-stack инженер и архитектор продукта. Не делай косметический рефакторинг — нужно именно перепроектировать текущую логику сервиса под официальные API Яндекса. Сначала изучи текущую структуру проекта, найди все места, где используются парсинг HTML SERP, прокси, антикапча, браузерные обходы, фоллбеки на публичную выдачу, и замени это на новую архитектуру через Yandex Search API + Wordstat API.

====================
1. ЦЕЛЬ ПРОДУКТА
====================

Новый сервис должен решать 3 сценария:

1) Search API
Пользователь загружает или вставляет готовый список ключей, выбирает регион, при необходимости указывает минус-фразы, а система анализирует конкурентность каждого ключа через Yandex Search API.

2) Wordstat API
Пользователь вводит тему или стартовый ключ, выбирает регион, задаёт минус-фразы и лимит, а система собирает и очищает семантику через Wordstat API.

3) Комбинированный режим
Пользователь вводит тему или стартовый ключ, выбирает регион, минус-фразы и лимит, а система сначала собирает ключи через Wordstat API, затем сразу анализирует их конкурентность через Search API и показывает итоговую таблицу.

Сервис должен быть ориентирован не на парсинг выдачи, а на конкурентный анализ семантики и SERP на официальных API Яндекса.

====================
2. ЧТО НУЖНО УБРАТЬ
====================

Из текущего MVP нужно удалить или отключить из пользовательского сценария:

- парсинг публичной HTML-выдачи Яндекса обычными HTTP-запросами;
- прокси;
- антикапчу;
- браузерный обход;

- генеративный поиск;

- ручную настройку группировки в UI;
- ручную настройку docsInGroup в UI;
- ручную настройку maxPassages в UI.

Если какие-то параметры нужны для API, оставь их как внутренние системные defaults в backend-конфиге, но не выводи пользователю.

Нельзя оставлять фоллбек, который продолжает тайно использовать старый парсер публичной выдачи. Нужно именно перейти на официальные API.

====================
3. ОСНОВНЫЕ API-ИСТОЧНИКИ
====================

Нужно использовать 2 источника данных:

A. Yandex Search API
Для анализа конкурентности по готовым ключам.

Поддержать внутри приложения 2 внутренних режима:

- Sync HTML — для точечной проверки SERP и диагностики;
- Async XML — для массового анализа ключей.

Пользователю необязательно показывать эти технические названия как есть, но в архитектуре и коде должны быть 2 отдельных контура.

Принципы:
- для точечной проверки SERP использовать HTML-ответ Search API;
- для массового анализа использовать XML-ответ Search API;
- Search API возвращает результат в поле rawData в Base64 — нужно декодировать и передавать в соответствующий парсер;
- HTML использовать для более “живого” SERP-анализа, включая рекламу и дополнительные SERP-элементы;
- XML использовать для стабильного машинного массового разбора.

B. Wordstat API
Для сбора семантики.

Обязательно реализовать:
- GetTop
- GetRegionsTree

Архитектурно сразу заложить расширение под:
- GetDynamics
- GetRegionsDistribution

====================
4. РЕЖИМЫ ИНТЕРФЕЙСА
====================

В верхней части интерфейса должен быть переключатель из 3 режимов:

- Search API
- Wordstat API
- Комбинированный режим

Нужно привести UI в соответствие этим трем сценариям.

--------------------------------
4.1. Режим Search API
--------------------------------

Показывать:
- большое поле для вставки ключей;
- кнопку загрузки файла;
- региональный селектор;
- поле минус-фраз;
- кнопку “Запустить анализ”.

Логика:
- пользователь может вставить ключи вручную;
- либо загрузить файл;
- система нормализует ключи;
- удаляет пустые строки;
- удаляет дубли;
- применяет фильтрацию по минус-фразам;
- запускает анализ конкурентности через Search API;
- показывает результат в текущей таблице анализа конкуренции без её переработки.

--------------------------------
4.2. Режим Wordstat API
--------------------------------

Показывать:
- поле “Тема / стартовый ключ”;
- региональный селектор;
- поле минус-фраз;
- поле “Лимит ключей”;
- кнопку “Собрать ключи”.

Логика:
- отправить запрос в Wordstat;
- получить популярные запросы и ассоциации;
- собрать единый список;
- удалить дубли, пустые записи и мусор;
- применить минус-фразы;
- ограничить список лимитом;
- показать таблицу собранных ключей.

Ниже результата:
- кнопка экспорта;
- кнопка “Отправить в анализ”.

Важно:
в таблице Wordstat должна быть возможность отметить чекбоксами:
- отдельные ключи;
- сразу весь список.

После этого пользователь должен иметь возможность отправить:
- только выбранные ключи;
- весь список ключей —
в режим анализа конкурентности.

--------------------------------
4.3. Комбинированный режим
--------------------------------

Показывать:
- поле “Тема / стартовый ключ”;
- региональный селектор;
- поле минус-фраз;
- поле “Лимит ключей”;
- кнопку “Собрать и проанализировать”.

Логика:
- получить ключи через Wordstat;
- очистить и отфильтровать;
- сразу отправить их в анализ конкурентности через Search API;
- показать итоговую таблицу анализа конкуренции в текущем виде, без переработки её структуры и логики вывода.

====================
5. РЕГИОНАЛЬНОСТЬ
====================

Региональный переключатель должен работать по логике Wordstat, а не через кустарный хардкод.

Требования:
- использовать GetRegionsTree как основной источник дерева регионов;
- построить UI-селектор на основе дерева регионов;
- не ограничиваться 5–10 регионами в коде;
- поддержать минимум:
  - Россия
  - Москва и Московская область
  - Москва
  - Санкт-Петербург
  - остальные регионы из дерева

Дополнительно:
- тот же выбранный регион должен передаваться в Search API как region и влиять на ранжирование;
- нужен единый адаптер маппинга выбранного региона для Wordstat и Search API;
- если API возвращает дерево в иерархическом виде, реализовать удобный селектор с поиском по названию региона.

====================
7. ЛОГИКА АВТОСБОРА КЛЮЧЕЙ
====================

Автосбор — это опция, а не обязательный этап.

Нужно реализовать базовый MVP-алгоритм:

1. Пользователь вводит тему или seed-key.
2. Отправляется запрос в Wordstat GetTop.
3. Из ответа берутся:
   - results
   - associations
4. Формируется единый список ключей.
5. Удаляются:
   - дубли
   - пустые записи
   - мусор
   - ключи, попавшие под минус-фразы
6. Итог обрезается по лимиту.
7. Возвращается очищенный список.

Важно:
- не переусложнять MVP;
- но архитектурно предусмотреть расширяемость, чтобы потом можно было добавлять рекурсивное расширение семантики, сбор в несколько проходов, дополнительные сигналы и т.п.

====================
12. ОБРАБОТКА SEARCH API
====================

Нужно корректно реализовать весь путь ответа Search API:

1. Отправляем запрос.
2. Получаем JSON.
3. Достаём rawData.
4. Декодируем Base64.
5. Получаем строку XML или HTML.
6. Передаём в нужный парсер.
7. Возвращаем результат в формате, который можно встроить в текущий pipeline анализа конкурентности без ломки текущей таблицы вывода.

Для async XML:
- отправка запроса;
- получение operation id;
- polling статуса;
- получение финального response.rawData;
- декодирование;
- парсинг XML.

Важно:
- предусмотреть таймауты;
- нормальную обработку ошибок;
- статус выполнения для UI;
- логирование request/response meta без утечки секретов.
