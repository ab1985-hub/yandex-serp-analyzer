Нужно доработать текущий сервис анализа конкурентности ключевых слов по Яндекс SERP.

Сначала разберись в проекте и пойми, как он сейчас работает.

Что это за сервис:
Это веб-сервис, в котором пользователь вставляет список ключевых слов, выбирает регион поиска, нажимает «Запустить анализ», после чего frontend отправляет запрос в backend, backend должен анализировать SERP по каждому ключу и возвращать результаты в таблицу.

Сейчас сервис уже визуально работает:
- форма открывается,
- ключи можно вставить,
- анализ запускается,
- таблица результатов отображается.

Но текущая проблема в том, что результатам нельзя доверять.

СИМПТОМ ПРОБЛЕМЫ:
По разным ключам сервис возвращает почти одинаковые результаты:
- одинаковый Strong в органике,
- одинаковый SEO score,
- одинаковый Ads score,
- одинаковый итоговый score,
- одинаковый класс,
- одинаковую рекомендацию.

Это выглядит как:
- либо мок,
- либо fallback,
- либо слишком грубая логика,
- либо анализ не идёт реально по каждому ключу,
- либо backend возвращает шаблонный ответ.

ТВОЯ ЗАДАЧА:
Найти причину, почему сервис даёт почти одинаковые результаты по разным ключам, и исправить это.

НУЖНО СДЕЛАТЬ ПОШАГОВО:

1. Изучи текущую логику backend-анализа.
   Пойми:
   - откуда берутся данные для анализа;
   - ходит ли backend реально в SERP;
   - анализирует ли backend каждый ключ отдельно;
   - нет ли моков, заглушек, fallback-ответов или шаблонных результатов.

2. Проверь, что реально происходит при анализе:
   - какой endpoint вызывается;
   - какой payload приходит;
   - как backend проходит по списку keywords;
   - не используется ли один и тот же результат для всех ключей;
   - не возвращается ли один и тот же score по умолчанию.

3. Если сейчас используется заглушка или упрощённая фиктивная логика —
   замени её на более честную диагностическую логику.

4. Добавь DEBUG-режим анализа.
   Это очень важно.

   Для каждого ключа нужно уметь увидеть:
   - какие именно данные были проанализированы;
   - какие заголовки органики были использованы;
   - какие описания были использованы;
   - какие рекламные заголовки были использованы;
   - почему присвоен strong / near / partial;
   - из чего сложился итоговый score.

5. Сделай так, чтобы backend возвращал для каждого ключа расширенный debug-блок.
   Даже если SERP пока упрощённый, нужно видеть логику прозрачно.

Пример того, что нужно вернуть в debug для каждого ключа:

- keyword
- raw_organic_titles: массив первых заголовков органики
- raw_organic_descriptions: массив первых описаний
- raw_ads_titles: массив рекламных заголовков
- organic_matches:
  - какие результаты получили strong
  - какие near
  - какие partial
- ads_matches:
  - какие результаты получили strong
  - какие near
  - какие partial
- score_breakdown:
  - из чего сложился seo_score
  - из чего сложился ads_score
  - почему получился total_score

6. После этого измени frontend:
   нужно добавить удобный способ смотреть debug-данные по каждой строке результата.

Варианты допустимы:
- кнопка «Подробнее»
- раскрывающаяся строка
- debug modal
- отдельный блок под таблицей

Главное:
по каждому ключу должно быть видно, что именно анализировалось и почему сервис дал такой результат.

7. Если сейчас логика анализа слишком примитивная и поэтому всё одинаковое —
   улучшить её хотя бы до уровня, где по разным ключам реально будут разные результаты.

То есть:
- убрать шаблонные одинаковые score;
- убрать одинаковые рекомендации по умолчанию;
- сделать результат зависимым от фактических данных анализа.

ВАЖНО:
Даже если пока нет полноценной интеграции с реальным Яндекс SERP API, всё равно нужно:
- убрать фиктивную одинаковость;
- показать прозрачную механику;
- сделать так, чтобы было видно, почему получился результат;
- сделать сервис пригодным для отладки и последующего усиления.

ЧТО НУЖНО В ИТОГЕ:

1. Backend действительно анализирует каждый ключ отдельно.
2. Результаты больше не выглядят как одинаковый шаблон.
3. По каждому ключу есть debug-информация.
4. Во frontend можно посмотреть:
   - какие заголовки анализировались,
   - какие совпадения нашлись,
   - как сложился score.
5. Если причина была в моке/fallback — убрать это или явно пометить.
6. Если сейчас используется fake-анализ — сделать это честно видимым в интерфейсе.
